# CI Pipeline Standard

This document governs how an Aurum Alpha repository builds, gates, versions
and publishes, and the shared job catalog in `aurum-alpha/workflows` that
implements it.

## Principles

### 1. One source of truth per pin

`.node-version`, `go.mod`, `.php-version`, `packageManager`: CI *derives*
versions (`node-version-file`, `go-version-file`) and never restates them. A
version bump is a one-file diff.

This binds container images too. A Dockerfile that needs a version at build
time reads the pin file. It does not get a copy of its own. Two files naming
the same version is a pin that will eventually disagree with itself. The image
then bakes a different toolchain than the one developers and CI run.

A validation step comparing the two copies is not a fix. It is a second thing
to maintain, guarding a duplication that must not exist.

The pin also lives beside what it pins. The node app directory owns its
`.node-version`, because that is where the shared jobs look
(`<workdir>/.node-version`).

### 2. Local = CI

A developer must be able to run any gate locally with one command, and get
what CI gets. **The shared job is that command's single definition**, not a
per-repo script it wraps.

**No logic exists only in YAML**. A shared job runs a tool with flags, such as
`pnpm exec oxlint client --type-aware --deny-warnings`, which a developer can
read off the job and run verbatim. It must not grow branching, conditionals or
computation that cannot be reproduced by typing the command. The moment a job
needs logic, the logic belongs in a committed script that both CI and the
developer invoke.

Repo-specific *policy* goes in the repo. It goes there as configuration the
tool reads (`vite.config.ts`, `.oxlintrc.json`), never as a wrapper script
whose job is to pass a path.

### 3. Fail closed

Nothing publishes unless every gate passes. `continue-on-error` is allowed only
as a documented stabilization window with a ticket reference and an expiry
expectation.

### 4. Standard runner line

`runs-on: ${{ vars.RUNNER || 'ubuntu-26.04' }}`, and that includes the
repository that builds the runners. The fleet builds on the fleet. A change to
the runner image is then exercised by the pipeline that produced it, before it
reaches any other repository.

The escape from a broken fleet is `vars.RUNNER` itself. It is a repository
variable, so a fleet-down repair is unsetting it and re-running, not editing a
workflow under pressure.

Runners are ephemeral, one container per job, so a hosted label buys no
isolation the fallback does not already give. A job that pins one anyway is
making a decision, and the comment above it says which. An undeclared literal
is drift.

### 5. Ephemeral-runner assumptions + provisioning tiers

No workspace-hygiene steps. Where a dependency lives is decided by tier:

- **Tier 1, runner image**: universal, host-level only. That means docker,
  git, core libs (libatomic1). Test: *every* repo's jobs would break without
  it. Nothing repo-specific.
- **Tier 2, builder image**: the exact toolchain when it is heavy,
  version-critical, or lacks a good setup action (PHP + extensions +
  composer). Self-bootstrapping rebuild when version files / image inputs
  change.
- **Tier 3, job steps**: lightweight toolchains with first-class actions
  (`setup-go`, `setup-node` + lockfile-keyed caches) and *runtime* deps via
  service containers / compose.
- **Policy: tier 3 is the standard; tier 2 only where actions fall short**.
  Builder images exist to work around action deficiencies, and that is their
  only justification. Where a gap is small, prefer a custom action in
  aurum-alpha/workflows over a builder image. Where a shared stack image
  exists (`ci-node`, `ci-go`, `ci-php`), it publishes from
  aurum-alpha/workflows and is consumed by digest.

### 6. Concurrency everywhere

`${{ github.workflow }}-${{ github.ref }}` + cancel-in-progress on pull
requests. But **never cancel a run that can publish**, which means never
cancel the default branch:
`cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`.

The exemption keys on the ref rather than on a workflow file, because
Principle 17 puts publishing inside `ci.yml`. A cancelled run is not a failed
one, so nothing reports a release that a later merge cancelled.

Publish jobs that need stricter serialization than the workflow (an image tag
several runs race to move) take a job-level `concurrency:` group of their own.

### 7. BUILD ONCE

The `build` job is the only compiler anywhere. It produces every required
artifact variant. Packaging, docker, and release steps consume those
artifacts, and nothing downstream rebuilds.

**For Go, that means exactly one `go build` per binary per architecture, and
nothing else**. Two binaries on two architectures is four builds, and four is
the number of build commands the job runs. `go build -o <out> ./cmd/<name>`
compiles *and* links in one command. There is no separate compile step to add.

In particular, **no `go build ./...` before the real builds**. It compiles
every package in the module, including ones no binary imports. The job's
promise is that every production artifact compiles, and each artifact's own
build proves exactly that. A package no binary imports is not a production
artifact and does not get to fail the build.

**Every upload declares how long it keeps**. An artifact passed between jobs
is a hand-off inside one run, and one day is long enough. The catalog's own
uploads all say `retention-days: 1`. Artifact storage is an org-wide quota;
an undeclared upload inherits ninety days.

The rule is that a number is stated, not which number. Where an artifact is
the only durable copy of a deliverable (firmware in a repository with no
release pipeline), a long retention is correct. The fix for the storage it
costs is to give that deliverable a real home, never to shorten the only copy.
Rule `RET` in `tools/check-ci-conformance` asserts presence and does not judge
the value.

### 8. No multi-stage production Dockerfiles

Shipped images are thin runtime images that COPY the prebuilt `dist`/`bin`
artifact. Dev images can compile for local HMR; the rule governs shipped
images.

### 9. Canonical script names, specific not generic

The *type* of check is in the name (`typecheck`, `test:unit`, never `check`).
The names, their bodies, and which repo shape carries which are
[`015-commands.md`](015-commands.md).

**The catalog defines the command, and the repo's script equals it**.
`check-package-scripts` holds that. A script is how a person reaches the
definition, never a second copy of it.

### 10. Lint output goes through standard channels

Default/stylish output + setup-node's built-in problem matchers (inline
annotations for free), plus optional `$GITHUB_STEP_SUMMARY` totals. No custom
PR-comment machinery.

### 11. Registry auth lives in user-level npmrc, never project `.npmrc`

pnpm 10+ ignores auth settings in project npmrc (supply-chain hardening), so a
project-level `_authToken` line is silently dead. CI gets it via setup-node's
`registry-url`; Docker builds and compose commands write `~/.npmrc` before
install; hosts via dev-init. The standard pnpm version is the one in
`dependency-versions.json`, declared through `packageManager`.

### 12. One way per capability

The unit of CI consistency is the *capability*, not the repo. A repo that has
a React frontend builds, artifacts, and tests it the ONE standard way. A TS
codebase is linted the ONE way, a Go backend is built/vetted/tested the ONE
way, and PHP likewise. Repos differ only in *which* capabilities they compose
and in the `needs:` wiring between them, never in how a capability is
executed. This is realized as single-job reusable workflows (one shared
definition per capability job) consumed by every repo with that capability,
single- or dual-stack alike.

### 13. Every artifact carries its provenance

Build timestamp and commit SHA are baked into every artifact at build time and
surfaced by the software itself. For Go that is `-ldflags`; for TS and PHP it
is a generated file at a fixed path in `dist/`, read through one helper. This
is not a version. It is metadata, it needs no scheme and no bookkeeping, and
it is why CalVer is not used. A timestamp and a SHA answer "how old" and
"which commit" exactly, on every build. A date-shaped version answers them
worse and demands increment rules and a validator.

### 14. A version is a commit, not a tag

Where a repo has a version, it lives in a committed file and the build stamps
what that file says. Tags are mutable pointers, which is the reason we SHA-pin
every third-party action. Trusting our own is the same bet with the same
downside. A version in a file is immutable, reproducible from history, and
*reviewable*: the claim "this release is 2.0.0" arrives as a diff someone can
challenge. CI can create a tag afterwards as a human index; the direction is
always file → build → tag, never tag → build.

### 15. The repo is versioned, not the artifact

Artifacts built from one commit share one provenance and therefore one
version. A repo shipping three images does not give them three version files,
for the same reason a repo does not pin pnpm twice. Something in the repo that
is not built from its source (a base image rebuilt on a schedule) is not a
versioned product at all. It carries provenance metadata and nothing else.

**Which artifacts share an image is decided by three things**: the dependency
closure, the credential, and the configuration surface. Where all three are
the same, code shares an image; where one differs, the image splits. An image
therefore does one thing. It is a server, or a worker, or the migrate step, or
a browser bundle, never more than one of those. A server and a worker differ
in closure, configuration and scaling. The migrate step differs in credential
([`025-structured-data.md`](025-structured-data.md) SD3), and a bundle differs
in all three.

A repository holding several services builds a full set of images per
service, because their credentials differ. Two stacks that ship together are
two images of one run bound by its version, not one image bound by its
contents. How workers apply the three criteria is
[`035-workers.md`](035-workers.md) WK2's.

### 16. A version is required where something consumes it, and allowed anywhere

**Required** where anything outside the repo makes a decision from the version
string. When apt compares versions to decide upgrade against downgrade, it
does. A dependency resolver does. `docker compose pull :latest` does not. A
repo with a consumer like that carries a version file, because provenance
alone is not enough to decide anything.

**Allowed** everywhere else, for whatever reason the repo has. The common one
is that people need to name a build out loud. That happens in a release note,
a support thread, or an instruction to roll back. A number a person can carry
through a conversation beats a commit SHA nobody reads back correctly. That
reason stands on its own and needs no consumer behind it.

What a version does, once a repo has one, is the same either way. Principles
14, 15 and 17 hold, and so do the rules under **One versioning
implementation**. Adding one later is a version file and a job that reads it,
never a scheme of its own.

### 17. Release is promotion, not production

A release publishes bytes that already exist and already passed: same
artifact, new name, wider audience. It never compiles, never re-tests, and
cannot change what is shipped.

It follows that publishing is a conditional job inside the normal CI run, not
a separate workflow. The run that built and gated the artifact is the run that
publishes it. So there is no cross-run artifact fetch and no question of which
build a release came from. It also means the publish path is exercised on
every pull request, with only the final push suppressed. Otherwise it is the
least-tested code in the repo at the exact moment it matters most.

Two mechanical consequences:

- **The main-only condition goes on the publishing *step*, never on the
  job**. `if:` at the job level means the job never runs on a pull request.
  Its first execution ever is then the one that has to work. Guard
  `docker push` / `gh release create`, and let everything above it (artifact
  downloads, packaging, assertions) run on every PR.
- **Publish jobs belong in `ci-ok`'s `needs:`.** A publish job outside the
  rollup can fail into a green required check.

### 18. One workflow per repo

`ci.yml` IS the pipeline. A second workflow file cannot be gated by `ci-ok`,
so branch protection cannot see it, so nothing stops it publishing from a
commit that failed. Nothing reviews it against the rules the rest of the repo
follows either.

Work in a repo that genuinely shares no source with the rest (a base image
rebuilt on a schedule) still lives in `ci.yml`. It is split by a `changes` job
so a Dockerfile edit does not compile Go and a code change does not rebuild an
unrelated image. Where two things need different concurrency, use a job-level
`concurrency:` group rather than a second file.

### 19. The catalog is where best practice lives; a repo-local job is a gap in it

`aurum-alpha/workflows` is not a convenience library of things several repos
happened to need. It is the definition of how this organisation builds,
lints, tests and ships each language and framework it uses. Repos are
standardized *onto* those definitions rather than each arriving at its own
answer.

The target state is a repo with **no repo-local jobs at all**. Its `ci.yml`
names its deployable units, wires the DAG, and calls the catalog.

A repo-local job is therefore not a style violation, it is a **claim about
the catalog**: *"nothing here covers this case"*. That claim is sometimes
true. Packaging a `.deb` with nfpm, or building an image from a vendor's base
that carries no source of ours, is work one product does. No shared job
models it. It is often false, and then the fix is a catalog job, not a local
one.

**The job id is what separates the two, and it is not advisory**. A job id
that names a catalog capability must be a stub calling that catalog job, with
whatever inputs it declares. A job id that names no catalog capability is
repo-specific, and the standard says nothing about it. Not what it contains,
not what it is called, not where it sits. That is the whole test, and it runs
on the tree rather than on a list of exceptions.

**What a job is, is read off the workflow it calls**. Every catalog job
declares its capability, language and role on its first line. The checker
resolves a caller's job through its `uses:` line to that declaration (rules
ROLE and DECL). A job calling no catalog workflow has no role, and no rule
infers one from the letters in its id. An id is evidence about a job the
standard names; the `uses:` line is the job.

The catalog holds no register of which repositories are permitted which local
jobs, because such a register goes stale into permanent, silent waivers.
Converting a repo-specific job is a review question, never a gate finding.

### 20. Production is the default; a job id marks the exception

The point of CI is to produce a production-worthy build, so a `-prod` suffix
says nothing: every unsuffixed job is already on that path. What needs marking
is the opposite: a job whose output is only good enough for tests. That one
takes `-dev`.

The test is whether a reviewer can tell, from the job id alone, whether that
job's output is allowed to ship. `install` and `install-prod` fail it in the
worst way, by implying the unsuffixed one is the shippable default when it is
the test-only tree.

Name the tool, not the framework, when the job is about dependencies.
`server-go-mod` is named for `go.mod` and `server-php-composer` for composer,
because neither dependency manager is framework-specific. Naming them for the
framework invites a second copy the day a second framework appears in the same
language.

### 21. A dependency tree that ships is a build output. One that does not is a cache

Which one you have is decided by the language, not by preference, and the two
are not interchangeable.

Compiled and bundled stacks discard their dependencies. A Go binary is static
and `node_modules` is transpiled away, so the module cache and the pnpm store
are pure speed. They get no job of their own: every job installs what it needs
from a lockfile-keyed cache, and losing one costs time, never correctness.
`go-mod` is the apparent exception and is not one: it exists for
`go mod verify`, which is a claim, not a cache.

Interpreted stacks ship theirs. PHP has no compile step, so `vendor/` is
copied into the image and *is* part of the artifact. That makes it a build
output under Principle 7: built once, published as an artifact, downloaded by
whatever assembles the image. It is never handed between jobs through
`actions/cache`.

The distinction matters because a cache fails open. A job that installs only
on a cache miss can publish nothing and still pass.

## Standard job DAG — build first, per artifact

**Fail fast.** If the thing does not compile, there is nothing worth testing.
So the first gate is always "does it build", and no lint, vet or test runs
until it passes. A broken compile fails one job in seconds instead of ten jobs
in minutes. It fails with the one error that caused the other nine.

The build job also produces and stores the artifact every later job uses.
Nothing runs beside it; everything runs after it.

```
build ──┬─► lint ──────────┐
        ├─► vet ───────────┤
        ├─► typecheck ─────┼─► integration / e2e ─► image ─► image starts ─► ci-ok
        └─► unit tests ────┘   (uses the build artifacts)      (fire it up)
```

In order:

1. **build**: compile, and upload the artifact. For TS that is `vite build` for
   the client and `esbuild` for the server; for Go, `go build`; for firmware,
   `pio run`. One build per artifact, and it happens once (see BUILD ONCE).
2. **codebase gates**: lint, vet, unit tests, typecheck. These run in parallel
   with each other and only after the build has passed. A repo whose code does
   not compile has nothing worth linting.
3. **integration / e2e**: against the artifacts from step 1, never a rebuild.
   This is the first point at which the thing under test exists.
4. **image / package**: the shippable artifact, assembled from step 1's output.
5. **something runs the image.** A build that links and an image that boots are
   different claims, and only the second one is what ships. There are two ways
   to satisfy this, and the requirement is the rule rather than either
   mechanism:

   - **e2e or integration tests against the container.** This is strictly
     stronger. It proves the image runs *and* that it does its job, and where
     this exists nothing else is needed. The image is then built before step 3
     rather than after it, because the tests need it.
   - **start it.** For a service with no e2e suite, run the container and wait
     for it to listen. `job-image-starts` does this.

   A repo taking the first route sets `assert_starts: false` on the image job.
   That is only legitimate when a job actually depends on that image, which D7
   checks rather than takes on trust. If the container needs a database to
   reach the point of listening, give it one (`start_services`). An image that
   cannot start without postgres is not exempt from having to start.
6. **`ci-ok`**: the rollup, and the only required check.

- **Quality gates run in parallel with each other, never serialized among
  themselves**, and never beside the build.
- **Every job sets `timeout-minutes`.** A runner that hangs reports the same
  failure a real break does, and takes the default six hours to say so.
  Ceilings are generous enough never to clip honest work, and exist only to
  bound a hang. They are 15m for gates, 20m for Go lint and tests, and 30m for
  image jobs.
- Stack note: for TS, `tsc --noEmit` is the compile assertion and stays a gate.
  "Build" means the real bundle/transpile (vite/esbuild), which is where the
  production artifact is produced.
- **The conformance job is the one gate that does not wait on the build**. It
  reads `ci.yml` and `package.json` and never a build output. A broken build
  therefore makes its verdict no less true. Gating it would mean the repo
  least likely to be conformant is the one that never finds out.
- **Every job must also be reachable from `ci-ok`.** Having a `needs:` and
  blocking something are two different properties. A job can sit correctly
  downstream of the build and still be absent from the rollup, in which case
  its failure stops nothing.
- `ci-ok` (`if: always()`, fails on any failure/cancel in needs) is the single
  required check, so adding/removing gates never touches branch protection.
  The check reports under the job id `ci-ok` (no display-name override).
  That exact string is what branch protection requires, in every repository.
- **`always()` and not `!cancelled()`.** A push that supersedes an in-flight
  run cancels its jobs, and `ci-ok` then runs, sees `cancelled`, and goes red.
  So every quick follow-up push leaves a red check behind on a run nobody
  cares about. The tempting fix is `if: !cancelled()`. That skips the rollup
  when the *run* was cancelled, while still catching an individual job that
  was cancelled by its own timeout.

  Do not. A skipped required check can satisfy branch protection, so a
  cancelled run would leave a PR mergeable with no gate having reported. The
  noise is the cheaper failure: a stale red is confusing, a silent green is
  dangerous. Read the newest run, not the superseded one.

### Standard gates run before repo-local ones

Inside the gate layer, order by origin:

1. **Standard gates**: the catalog calls every repo of that stack runs:
   `fmt`, `vet`, `test-unit`, the linters, `govulncheck`, `osv-scan`.
2. **Repo-local gates**: the policy a repo enforces about itself. A
   forbidden-import check, a telemetry canary, an expand-only migration
   check, header definition and staleness checks, a golden corpus, a contract
   suite, an image-tag parity check.
3. **Integration and e2e**: anything that stands a database, a broker or a
   browser up to test against.

Each names the tier before it in `needs:`, entry by entry. No convergence job
stands in for the list. The rollup already proved that a job's failure is
only visible where it is named. An intermediate node would put one more place
between a failure and the thing that reports it.

**Why, beyond looks.** It is `build first, fail fast` one level up. A
repo-local rule failing is a narrower answer than `vet` failing. Suppose the
code does not pass the gates every repo shares. Then "and it also violates the
forbidden-import rule" is noise on top of a verdict you already have. Cheap and
universal first, bespoke second, infrastructure-standing third.

It is also the only way to show the distinction. GitHub's workflow graph lays
jobs out by dependency depth alone, so standard and repo-local look different
only by being different depths.

Cost: the slowest repo-local gate joins the critical path.

**An empty tier is not a stage.** A repo with no repo-local gates has nothing
between its standard gates and packaging. Absence is a fact about the
repo, not a hole to fill with a placeholder.

**The job ids do not change.** Check names are what branch protection in
every repo depends on. A `repo-` prefix would rename every check to buy a
label the graph already shows by position.

### Multi-codebase repos — one DAG per stack, converging at packaging

A repo can hold two codebases in one tree: a React client beside a Go server,
a Node server, or a PHP server. **Each stack runs the standard DAG
independently, and they converge only at packaging and integration.** All of
it lives in the one `ci.yml` (Principle 18). A second stack is not a second
workflow.

```
web-build ───► web-lint ──────────┐
          ───► web-typecheck ─────┤
          ───► web-test-unit ─────┤
                                  ├──► image / package ──► test-integration ──► ci-ok
api-build ───► api-lint ──────────┤          (converge)
          ───► api-test-unit ─────┘
```

- A stack's gates depend on **that stack's** build and nothing else. A failing
  Go vet must not hold up the React lint. A broken `tsc` must not stop the
  Go tests from telling you what else is wrong. Cross-stack `needs:` serialize
  two independent pipelines into one long one and hide half the failures behind
  the other half.
- The convergence point is the first job that needs every stack's build. That
  is the image jobs, one per image, and the start check that runs the images
  together. Two stacks ship as separate images bound by the run's version
  (Principle 15), so the convergence is the run and not an image containing
  both. That job needs every stack's build **and** every stack's gates. It is
  the first place a cross-stack failure legitimately blocks something.
- Integration/e2e sits after the converged artifact, because that is the first
  point at which the thing under test exists.
- Naming follows the job-id rules below. A bare `lint` in a two-stack repo
  reads as whichever stack the reader assumes, so both get a prefix
  (`web-lint`, `go-lint`).

## Releasing the catalog

**Every repository tracks `@main`. There is no opt-out from the current standard.**

A repository references a catalog job as
`aurum-alpha/workflows/.github/workflows/job-x.yml@main`, and rule **PIN**
requires exactly that: not a sha, not a tag. A change merged here is live in
every repository on its next run. With callers on `@main` the workflow and its
checkers come from the same commit.

Pinning is the alternative, and it sounds right: each repository gets a stable
set of rules that changes only when it chooses. But a repository that can sit
on an older catalog can decline a rule indefinitely without ever saying so.
A rule nobody has adopted is not a standard. The loop pinning produces,
change the catalog, bump every pin, discover the bug, fix, bump again, is
itself the dominant source of breakage.

**The blast-radius argument survives its own answer.** A bad merge here does
break every pipeline at once. The fix is to merge the correction here and
re-run, and nothing stands in the way of that. This repository's own `ci.yml`
calls its jobs by local path, so a catalog that breaks every consumer cannot
break the repository that repairs it.

Third-party actions stay sha-pinned; that is a different rule (Action pinning,
below) that happens to share a syntax.

### Versions are still cut, and still mean something

They stop being how a repository consumes the catalog. They remain how a human
names a state of it.

- **`.version` is a committed file**, `MAJOR.MINOR.PATCH`. Principle 14's
  direction, unchanged: file → build → tag, never tag → build. The claim "this
  is 2.4.0" arrives as a diff someone can challenge.
- **A release is its own pull request**, touching the version file and prose
  and nothing else. `job-version-gate` refuses anything wider.
- **CI tags `main` with it** after `ci-ok`, alongside the other housekeeping
  downstream of the rollup. Created once, never moved: if the tag already
  exists on a different commit the job fails rather than repointing it.

### A CI result is a point-in-time assertion, and re-running does not renew it

**A green run means: this tree passed the standard that was live at that
moment.** That is the entire claim. It is not a promise about tomorrow's
standard, and no run, on a branch or on `main`, has ever carried one.

Three consequences:

**A re-run is not a refresh.** GitHub records the commit each `@main` reference
resolved to when the run was queued. A re-run replays exactly those. So a
re-run cannot pick up a newer catalog, and asking it to is a misreading of what
it is for. It re-executes a run, it does not re-ask the question. Getting the
current standard's answer takes a *new* run, which is what any push produces.

**A run against a superseded head is worse than useless, and re-running one is
harmful**. The workflow-level concurrency group is per-ref and cancels in
progress on every ref but the default branch. So restarting an old run
re-enters that group and cancels the live one. The result is a cancelled run on
the commit that mattered and a completed run on a commit nobody will merge.
Before re-running anything, check that its head is still the branch's head.

**A pull request that has fallen behind is not owed its old verdict**. Bring
the branch up to date and let CI run again against the standard as it is now
(see "Up to date before merging", below).

## Publishing

- Registry: ghcr. Tags: `<sha>` always; `latest` only on the default branch;
  `pr-N` build-only (no push).
- **Every green build publishes.** A run that passes the gates makes its
  artifacts available, release or not: images under `sha-<short>`, build
  outputs as run artifacts. Anything green is installable and testable
  without ceremony. That availability is the normal state, not a privilege a
  release confers.
- **What a release adds is a name, durability and an audience, never
  different bytes**. A release republishes the identical artifact under a
  stable version, in the place its consumers already fetch from
  (Principle 17).
- **SemVer is the only version scheme**, for every repo that has a version
  (Principle 16). Which repositories have one is not recorded here: a census
  inside a rule reads as the rule, and goes stale without anything failing.
  CalVer is not used anywhere: provenance metadata answers recency better
  (Principle 13). A repo with no version file runs no release step, and
  deploys from `latest` or a SHA.
- **Per-branch images: deferred** until per-branch staging spin-up/teardown infra
  exists. Revisit then.

### One versioning implementation, and no repo defines its own

**A repository does not decide its own versioning semantics**. Three things
are standard rules, stated here and nowhere else. They are when a release is
cut, how a build between releases names itself, and what is permitted to be
emitted. A repo's `AGENTS.md` points at this section; it does not restate it.

The rule is one thing; the implementation is one thing **per build system**,
and both live in the catalog:

| Build system | Implementation | Exposes |
| --- | --- | --- |
| Go | `job-go-build` | `version`, `version_changed`, `stamp` |
| C/C++ via PlatformIO | `job-build-cpp-pio` | the same three, plus `AURUM_VERSION_STAMP` in the environment |
| JS via Vite | `job-build-js-vite` | the same three, and `stamp` goes nowhere: a bundle has no linker |
| No build (a repo whose only version-named emission is its tag) | a repo-local job reading the version file | `version`, `version_changed` |

The Vite job hands out `stamp` and puts it into no artifact. What every repo
shares is the *decision*: is this a release, and what is a mid-stream build
called. A JS repo that later grows a provenance file
(Principle 13) reads that string rather than deriving a second answer.

**One catch belongs to callers with a nested client**. The version is the
repository's, not the JS project's (Principle 15), so `version_file` is
relative to the repo root and not to `workdir`. A repo whose client sits in
`client/` still keeps one `.version` at the top, and the job reads it there.

**And the minting is one implementation for all of them: `job-version-release`**.
It takes `version` and `version_changed` from whichever build job produced them
and does not re-derive either. The build jobs share one byte-identical
decision block, and `tools/check-version-stamp-shared` holds the copies
identical.

Rendering is per-ecosystem; deciding is not. A packaging job renders; it never
re-decides.

**A version built for a package manager obeys that package manager's rules,
not ours**. The version string and the artifact name go to a resolver we did
not write, whose ordering and validity rules are already fixed. Where our
SemVer spelling and the target's disagree, the target wins: the target is what
sorts the versions and decides upgrade against downgrade. A string that is
valid SemVer and wrong to the tool reading it is wrong.

The shape of the clash repeats per ecosystem. dpkg reads a character we use to
mean pre-release as a field separator. Python normalizes a version before it
compares one. A container tag admits a narrower character set than SemVer
emits. Each is a translation, and each belongs in the job that packages,
beside the artifact it names.

So a packaging job states its target's rule where it renders, and proves it
with that ecosystem's own comparison tool. Reading the spelling is not proof.
`dpkg --compare-versions` answers for a `.deb`, and nothing else does.

**An image's `org.opencontainers.image.version` label is one of those
renderings, and `job-image-build` takes it as an input**. The job carries no
copy of the decision block and must not grow one. It packages what a build
system already produced, so it is handed the answer rather than deriving a
fourth.

Callers pass `stamp`, not `version`. `version` is what the last release was
called, and a mid-stream image labelled with it claims every merge is that
release. Left unset the label reads `dev`, which is what the build jobs return
for a repo with no version file.

**A bench build is the one honest remainder**. A build on a workstation has no
CI job to ask, so a repo can compute the same answer locally. But it consumes
the stamp the catalog job supplies whenever there is one, and the local path
exists for the local case only.

### Only a version change mints a version

**A version-named emission is produced only by a commit that changed the
version file**. A git tag, a `v<version>` image tag, a GitHub release, a
versioned package: all of them key on that one question. Nothing else about
the build does. Provenance-named emissions are unconditional. Every green build
still publishes `sha-<short>`, moves `latest` on the default branch, and
uploads its run artifacts.

Three consequences:

- **Main is not versioned at every commit, and that is the design.** Work
  merges without a version. Everything between two releases is built, gated
  and installable under `sha-<short>` and `latest`; it is simply not minted.
- **A release pull request changes the version file and prose, nothing else.**
  Enforced by `job-version-gate`, and minted by `job-version-release`. The
  bytes a release mints are then a build of a tree main has already proved.
  The reviewer approving it is approving a release rather than approving a
  change and getting a release with it.
- **Mid-stream builds say so in their own version string**. Go binaries stamp
  a SemVer **pre-release of the next patch** on any commit that did not change
  the version file. So `0.15.0` in the file becomes `0.15.1-dev.<sha7>`
  (`job-go-build`'s `stamp` output).

  The next patch is a floor, not a guess. Whatever the next release turns out
  to be, it is at least `0.15.1`. So the stamp is correctly ordered against a
  version nobody has chosen yet:

  ```
  0.15.0  <  0.15.1-dev.abc1234  <  0.15.1-rc.1  <  0.15.1  <  0.16.0  <  1.0.0
  ```

  Build metadata (`0.15.0+dev.abc`) is wrong. SemVer ignores it in precedence,
  so that build compares *equal* to the release it is not. And the identifier
  is `dev` rather than `beta` because `-beta.N` and `-rc.N` belong to
  pre-releases a human cuts deliberately. An automatic per-commit stamp must
  not spend those words. Ordering is unaffected: `dev` < `rc` by SemVer's
  ASCII rule.

  **A `.deb` is not this string.** dpkg reads `-` as the separator before the
  debian-revision, so `0.15.1-dev.abc` sorts *above* `0.15.1` there. Debian's
  sorts-below marker is `~`, so a packaging job wants `0.15.1~dev.abc`. That
  is the package-manager rule above in its sharpest form, and the translation
  lands with the job that packages.

**Adopting the gate needs one change to every push-gated job below `ci-ok`.**
`job-version-gate` is pull_request-only, so it is skipped on every push to
main. It has to sit in `ci-ok`'s `needs:` or it gates nothing. GitHub then
propagates that skip transitively to every job whose `needs` closure contains
it, because `always()` rescues only the job carrying it. `ci-ok` has one and
survives; the tag, release and publish jobs below it do not.

The failure is silent: the run is green and the job is absent. Every main-only
job downstream of `ci-ok` carries its own guard:

```yaml
if: >-
  always()
  && github.event_name == 'push'
  && github.ref == 'refs/heads/main'
  && needs.ci-ok.result == 'success'
```

The result check is not decoration. `always()` also disarms the implicit "only
if my dependencies succeeded", so without it the job would tag a commit whose
CI had failed.

**The version moves forward or not at all**. `job-version-gate` fails a pull
request that moves the version backward, repeats it, malforms it, or deletes
the file. A repeat is as fatal as a decrease. Tags are created once and never
moved, so the release step finds the tag, skips, and reports success, shipping
nothing, greenly.

### Main is reached only by merge, and a merge to main is the release event

Direct pushes to the default branch are blocked org-wide. Every change reaches
`main` through a pull request whose `ci-ok` is green. That means a required
status check, branches required to be up to date before merging, no required
approvals, no merge queue. **Squash is the merge method**, so one merged pull
request is one commit on `main`. The head branch is deleted on merge, because a
squashed branch holds nothing that `main` does not now hold.

A merge fires `push` on `main`, so publish jobs run only after a green pull
request. A pull request run builds the artifact and proves it, pushing
nothing: images under `pr-N` without a registry push, build outputs as run
artifacts. A main run is the release event: same DAG, same bytes, plus the
publish steps.

**Up to date before merging is on, org-wide, and it is what makes the green
mean anything**. GitHub tests `refs/pull/N/merge`, the branch merged into the
base as it then stood. So a pull request that went green before `main` moved
is a proof about a merge result that no longer exists.

Strict mode closes that. The head branch must contain the current tip of
`main`, and GitHub re-checks it at the moment of merge. So the tree that was
proved and the tree that lands are the same tree. Post-merge `main` runs stop
being the thing that catches a semantic conflict and go back to being what
they are, the release event.

What it costs is throughput. Every merge to `main` stales every other open pull
request, each of which then needs its branch updated and a new run gone green.
With several open at once, the order they land in stops being free.

Two things this does **not** buy:

- **The merge queue stays off**. A `ci.yml` that does not handle
  `on: merge_group` never reports the required check on that event. So
  `merge_group` in every `ci.yml` trigger is the prerequisite, and it comes
  first or not at all.
- **The gate is required by name, and the branch under test supplies the
  body**. Branch protection stores the string `ci-ok`, and a pull-request run
  executes the head branch's copy of `ci.yml`. So a pull request that trims
  `ci-ok`'s `needs:` list still lands a green check by that name. Review holds
  that gap; the gate that closes it is tracked in the issue tracker.

### CI does not commit to the repository it is testing

**Nothing generated by a build gets committed back.** Rule `CM` fails any job
whose steps run `git push`.

A job that stamps a file after the build and commits it to `main` gets three
things wrong:

- the image built in that run carries the **previous** commit's stamp, because
  the new one is written after the build has already happened;
- the pushed commit is marked `[skip ci]`, so the stamp it contains is never
  built into anything;
- the job needs `contents: write` on the default branch to do it.

The generated file is a build output, so it is produced **during** the build
and emitted into the build output. For a Vite client that is a plugin
emitting `version-info.json` into `dist`, which is the `/version-info.json`
the client already fetches. It describes the commit it was built from because
it is built from it, and there is nothing to commit.

`contents: write` for `gh release create` is unaffected: publishing a release
adds no commit to a branch. The rule is about commits, not about the permission.

### A start check must not destroy its own evidence

`docker run --rm` removes a container the moment it exits. A container that
exits is the one failure a start check exists to catch. So the cleanup's
`docker logs` runs against a container that is already gone:

```
##[error]fastgen exited before becoming healthy (state: removing).
Error response from daemon: No such container: a0745cb9ccd6…
```

**Start checks do not use `--rm`**. They remove the container explicitly in the
cleanup trap, after dumping its logs and the logs of any service container.

### Concurrency is per ref, and a pull request is not its branch

The group is Principle 6's. It keys on `github.ref`, and what that holds
depends on the event:

| event | `github.ref` |
|---|---|
| `push` | `refs/heads/<branch>` |
| `pull_request` | `refs/pull/<n>/merge` |

Three consequences:

**A newer commit on a pull request cancels the older run.** Same PR, same ref,
same group. This is what makes `ci-ok` go red on superseded runs (see
`always()` above).

**Different branches and different pull requests never cancel each other.**
Different refs, different groups. Any number of PRs run at once; the only limit
is runners.

**A push run and a pull request run for the same commit are in *different*
groups.** They cannot cancel each other. So if `push:` fires on feature
branches the entire DAG runs twice per commit, for the same answer. Hence rule
`TRG`: **`push:` lists the default branch only.** The pull request run already
gates the branch.

### Waiving the start check costs a sentence

Some images genuinely cannot boot in CI. An image that needs a hosted identity
provider at startup (`REPLIT_DOMAINS` and OIDC discovery against `replit.com`)
has no version that starts without it.

Letting the check fail and agreeing to ignore it leaves a default branch
permanently red. That teaches people that red means nothing and hides the
next real failure behind an expected one.

So `job-image-starts` takes `start_blocked_by`, and it is **a string, not a
boolean**, on purpose:

```yaml
    with:
      start_blocked_by: >-
        Replit IdP — needs REPLIT_DOMAINS and OIDC discovery against replit.com
```

The job prints the reason as a warning, skips the start check, and stays green.
Rule `D7` accepts it **only because it is non-empty**. An empty string is
reported as a violation, because a flag would say "this image is exempt"
without ever saying why or until when. A sentence names the blocker. That
makes the waiver visibly stale the moment the blocker is gone. It also makes
it greppable across every repository when someone asks which images nothing starts.

Read the preserved log before writing a waiver.

### Never write the skip token in a commit message, even to describe it

GitHub reads `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` and
`***NO_CI***` from **anywhere in the head commit's message, body included**. On
a match it creates no workflow run at all. Not a startup failure, not a skipped
run, nothing. The PR shows zero checks, which reads exactly like a long runner
queue.

A run publishes no check runs until its jobs are assigned to a runner, so zero
checks is ambiguous.

Write it as `skip-ci` in prose. Spelling it out in a file is fine; only the
commit message is scanned.

### Accepting a vulnerability: an id list, or a stage you can defend

`job-go-govulncheck` takes an `allow:` input (newline-separated `GO-YYYY-NNNN`
ids) and no `warn_only`. The difference is the point. A `warn_only` silences
the finding in front of you and every finding after it, including the one that
is exploitable. An allowed id stops blocking; anything not on the list still
fails the job. **Where the accepted set is small and stable, the id list is
the right instrument and remains the default.**

osv-scanner takes a different instrument. A first scan of a TS tree returns
dozens of advisories, and an id list that size is exemption by exhaustion. Unlike the Go findings, most of them have fixes.

So `job-osv-scan` splits the question. `fail_on_new` defaults true, so a pull
request is blocked by what it introduces from day one. `fail_on_existing`
defaults false, which is Principle 3's stabilization window held per repo
until its count reaches zero (see "The catalog wraps it", below).

It is a phase, not a setting:

1. **Get the job everywhere it belongs**, running and reporting. A repo that
   has never been scanned learns what is in its tree.
2. **Get the findings to zero**, repo by repo, against a tracked list.
3. **Turn it blocking**: `fail_on_existing: true`, which is where every gate in
   this document is meant to end up.

`fail_on_existing: false` is how a gate sits in stage 1 without either lying
about the tree or stopping every merge. The honest test for whether a repo is
still entitled to it is whether its findings are going down. A repo that has
not moved in a quarter is not in a phase, it is a decision nobody made out loud.

**Once a repo reaches stage 2, individual advisories are accepted in
`osv-scanner.toml`, not in CI**. The scanner reads it beside the lockfile
without being told to, filters by id, and prints the reason it was given:

```toml
[[IgnoredVulns]]
id = "GHSA-xxxx-xxxx-xxxx"
reason = "daemon-side defect; this repo is an API client and runs no daemon"
ignoreUntil = "2026-11-15"
```

The exemption lives beside the dependency it exempts, in the repo that owns
the decision. A `reason` must say what would make the entry removable.

**A blocking mode is not the only thing that can go wrong**. A missing lockfile
or a scanner that crashed fails the job in either mode, because neither is a
clean result. "Could not look" never reads as "nothing to find".

`job-go-govulncheck` counts **symbol-level** findings only: code the binary
reaches, not modules it merely requires. Every allowed id carries its reason at
the call site.

## Coverage

**A CLI `--coverage.exclude` replaces the config's list; it does not extend
it**. That is true of vitest's array options generally, in both directions. An
include flag replaces a curated include, and an exclude flag drops
`node_modules`, `dist`, `*.d.ts` and every `*.config.*` file back into the
denominator. So the shared job restates the standard exclusions alongside the
sibling units. A repo needing more than that baseline narrows
`coverage.include` in its config.

- **Codecov everywhere it can be supported**: `codecov/codecov-action` **v7**,
  SHA-pinned, `fail_ci_if_error: true`, thresholds in `codecov.yml`. The
  upload happens once per run, from `job-coverage-upload`, not from the test
  jobs. **One action for both kinds of report**: coverage and test results
  alike go through `codecov-action`, the latter with
  `report_type: test_results`. `codecov/test-results-action` is deprecated by
  its own maintainers; one action means one pin.

### A test job answers one question; uploading is a different question

A `test-unit` job that also pushes to Codecov reports one conclusion for two
unrelated outcomes. They are **did the tests pass**, and **did a third-party
service accept an HTTP POST**. Callers gate `image-build` on `test-unit`, so an upload
with no token skips every image job with nothing wrong in the code.

So the split follows the question:

| job | answers | a failure here means |
|---|---|---|
| `*-test-unit` | do the tests pass | the code is broken; gates must not proceed |
| `coverage-upload` | did Codecov take it | re-run this one job; nothing else is affected |

`coverage-upload` sits in `ci-ok`'s `needs:` and **nothing else depends on it**.
A Codecov outage turns one job red and leaves the pipeline running.

### The collector counts nothing

Test jobs publish artifacts named `coverage-*` and `testresults-*`;
`job-coverage-upload` globs those patterns and uploads whatever is there.

There is **no expected report count** anywhere, not in the job and not in
`codecov.yml`. A unit with no tests publishes nothing, a unit whose tests
failed publishes no coverage, and a repo can have one test job or five. Any
design holding an expected number would have to stay right about all of that in
every repo forever. It would be wrong the first time a unit gained or lost
tests. `download-artifact` treats a zero-match `pattern` as success, so the
empty case needs no special handling. It needs only a warning that says which
of the two innocent reasons it was.

One upload per run is the second reason the job exists. Codecov scores as soon
as it has a report (`codecov.notify.after_n_builds` defaults to 1). Uploads
arriving minutes apart therefore score partial data and re-score on each
arrival. One
upload means no partial state and no `after_n_builds` to keep in step with the
job graph.

**What this costs**. A flag is a property of an upload, so a single merged
upload cannot carry a per-unit flag, and nothing gates on one. Codecov
**components** (`component_management`) slice by path and give the same
breakdown back.

### Every unit emits JUnit, whatever the language

Codecov **Test Analytics** (per-test timings, failure rates, flaky-test
detection) reads JUnit XML. A unit that emits none is invisible to it however
green it is, and nothing says so.

Each toolchain produces it its own way, configured where that unit's test
command already lives:

| language | producer | configured in |
|---|---|---|
| TypeScript | vitest | `--reporter=junit --outputFile.junit=…`, shared test job |
| Go | gotestsum, wrapping `go test` | `--junitfile=…`, shared test job |
| PHP | phpunit | `<logging><junit>`, the repo's `phpunit.xml` |

Go needs a pinned wrapper binary, because `go test` has no JUnit mode. However
it is produced, the report is a `testresults-*` artifact the collector globs,
so a new language adds a producer and nothing else.

**Every one of these uploads gates on `!cancelled()`, never `success()`**. A
failed run is the signal Test Analytics most wants. Gating on success would
withhold exactly the runs flaky-test detection exists to find. Coverage is the
opposite and stays on `success()`, because a failed unit has no coverage worth
scoring.

## Action pinning — SHA everywhere

The same rule binds every Dockerfile `FROM` line, by digest with the version
in-band ([`085-security-baseline.md`](085-security-baseline.md) SB1); the
reasoning below is the reasoning there.

Version tags are mutable pointers. The tj-actions/changed-files incident
(2025-03) rewrote existing tags to malicious code, and SHA-pinned consumers
were untouched.

- Pin every action to a full commit SHA with a mandatory trailing `# vX.Y.Z` comment.
- Enable Dependabot (`github-actions` ecosystem) per repo. It maintains SHA+comment
  pairs, making upgrades reviewable PRs instead of silent tag moves.
- Workflow-level least-privilege `permissions:` blocks everywhere.
- Known limits: your SHA does not pin an action's own transitive deps, and a bad
  *new* release still needs review before you bump into it.
- Optional backstop: org-level allowlist of permitted actions.

## Version pinning — exact versions, no ranges

**A range in a manifest is forbidden.** No `^`, no `~`, no `>=`, no `*`, no
`||`. Every dependency is declared as the exact version it resolves to. This
is the package-manager half of SHA-pinning actions above, and it is settled
for the same reason: a mutable pointer is not a pin.

**A caret is a constraint, not a version.** `package.json` says what is
PERMITTED; the lockfile records what is INSTALLED. Both are authoritative and
they answer different questions. The mistake is reading the first as if it
answered the second. They drift apart the moment anyone runs an install, and
nothing announces it.

Repositories declaring `concurrently: ^9.2.1` each ran a different installed
version, and nothing was red: each lockfile was internally consistent, and a
lockfile cannot see another tree.

**The lockfile is not a sufficient answer.** It pins within a repository, and
CI runs `--frozen-lockfile` so a build is reproducible today. What it cannot
do is hold separate repositories to the same version, or stop the pin from moving
the next time somebody installs something unrelated.
`tools/check-dependency-versions` compares MANIFESTS for exactly that reason.
A cross-repository claim has to live somewhere a cross-repository checker can read.
A range gives it nothing to assert, since one range is compatible with many
installed versions.

An upgrade becomes an event, a Dependabot pull request with a diff and a
reviewer, rather than a side effect of an unrelated install.

**Scope: keys that decide what gets installed.**

| key | pinned | why |
|---|---|---|
| `dependencies` | **yes** | resolves to an install |
| `devDependencies` | **yes** | resolves to an install |
| `optionalDependencies` | **yes** | resolves to an install |
| `pnpm.overrides` | **yes** | rewrites a transitive resolution; a floating override is the same defect one level down. The top-level `overrides` and `resolutions` keys are forbidden outright; see **Dependency overrides** below |
| `engines` | **no** | a compatibility floor, not an install target. Nothing resolves from it, and an exact `node` would reject the next patch for no gain; the real version is pinned by `.node-version` |
| `peerDependencies` | **no** | a range is CORRECT here: a pinned peer forces one version on every consumer. An application declares none; a library repository would rely on this row |

Pin to the lockfile's resolved version, never to the range's floor.

`tools/check-exact-pins` enforces this, per repository, from
`job-ci-conformance`.

## Dependency overrides — the lever over code you do not own

An override forces a version on a **transitive** dependency: a package nobody
here declared, which arrived because something that was declared depends on it.
It is the only lever over such a package, and that is the whole reason the
mechanism exists.

A direct dependency ships its own specs inside a tarball on a registry, so
nothing in this repository governs them, and every alternative is heavier:

| instead of an override | what it costs |
|---|---|
| wait for the maintainer | their release schedule, not ours; for an unmaintained package, never |
| fork the dependency | we own a fork, a publish pipeline and every future merge |
| `pnpm patch` | a diff maintained against a moving target; right for a code change, heavy for a version |
| drop the dependency | rarely available |

An override is the cheap form of all four: one line saying that whatever
anything in this tree asks for, it gets this instead.

### Why a range upstream is correct and a range here is not

A range in a published library is load-bearing. It is what lets a patch
release reach every consumer without a coordinated release from every package
in the chain. A range in an application is rot, because nothing downstream
depends on its flexibility, so it buys nothing and costs cross-repository
drift. The lockfile lets both be true at once: the range says what is
PERMITTED, the lockfile what is INSTALLED, and re-resolving is a deliberate act.

**An override is for when the library's range is wrong**: capped below the
fixed version, too tight to dedupe, or naming a package nobody maintains. That,
and nothing else.

### Three keys, and only one of them belongs here

Node repositories are pnpm-only. Three override keys are in circulation, and
pnpm's treatment of them (measured) is not what their names suggest. The
target package resolves to `2.0.2` when nothing overrides it:

| key | whose | pnpm applies it? | measured |
|---|---|---|---|
| `pnpm.overrides` | pnpm | **yes**, and it wins | beats `resolutions` when both name the same package |
| `resolutions` | yarn | **yes** | applied when no `pnpm.overrides` names that package |
| `overrides` | npm | **no** | ignored even as the only key present; the target resolved to `2.0.2` |

**`pnpm.overrides` is the only key allowed.** The other two are forbidden, for
two different reasons that are kept apart:

- **`overrides` is forbidden because it does nothing.** It is worse than
  absent. A reader who finds it in a `package.json` has no way to see that it
  governs nothing. A manifest carrying the same entry under both keys reads
  as emphasis when it is one live copy and one corpse.
- **`resolutions` is forbidden because it works.** Two live keys, with a silent
  precedence between them, is two answers to one question. That is the failure
  this standards repository exists to prevent, arriving inside a single file.
  Which one governs a given package depends on whether the other happens to
  name it.

### When an override is allowed

Four cases, and they are the entire list:

1. **A vulnerability upstream has not fixed**: a CVE in a transitive
   dependency whose parent has not yet bumped.
2. **A package that has been abandoned**, including redirection to a maintained
   successor through an alias. An example is routing `drizzle-kit`'s dependency
   on the deprecated `@esbuild-kit/esm-loader` to `npm:tsx@4.22.4`, which is
   that package's own author's replacement for it.
3. **Deduplication that matters**: two dependencies pulling incompatible
   majors of one library where a single copy is required to work.
4. **A broken release** that a dependency's range permits and a newer version
   fixes.

Anything outside these is not an override. It is a dependency, and it is
declared as one.

### Every override carries its reason and its exit

An override rewrites the supply chain invisibly, survives every dependency
bump, and has no expiry. One with no stated reason cannot be told apart from
one that has been wrong for two years.

So each one is introduced carrying two things, in the pull request that adds it
and in the repository's own documentation:

- **what it routes around**: the CVE, the abandonment, the conflict; and
- **what retires it**: the upstream release, or the removal of the dependency
  that needed it.

Overrides are pinned exactly, like everything else. A floating override is the
pinning defect one level down, which is why the scope table above lists it.

The reason lives in `pnpm.overrideReasons`, beside the override it explains:

```json
"pnpm": {
  "overrides":       { "zod-validation-error": "5.0.0" },
  "overrideReasons": { "zod-validation-error":
      "eslint-plugin-react-hooks imports zod-validation-error/v4 but declares
       ^3.5.0 || ^4.0.0. Retires when the resolved version exports ./v4." }
}
```

It lives beside it, and not in a file of its own, because a reason that lives
elsewhere drifts away from the thing it explains. The key is ignored by pnpm,
so it costs nothing at install time. `tools/check-overrides` enforces the
pairing from `job-ci-conformance`. It rejects the forbidden keys, an override
with no reason, and a reason left behind by an override that has been removed.

## Dependency updates — every manifest gets a watcher

Action pinning above covers one ecosystem. This is the rule for the rest.

**Two mechanisms, and only one of them is configured**. GitHub enables
*security updates* by default; *version updates* happen only where an
`updates:` entry names the ecosystem. An unwatched manifest is therefore not
unprotected but frozen, drifting until a CVE forces a jump across several
majors at once.

**Every ecosystem with a manifest in the repository gets an `updates:` entry**.
`directories` (plural) accepts a list and globs, so a repo carrying two trees of
one ecosystem needs one entry, not two.

**One grouping shape, everywhere:**

```yaml
    schedule:
      interval: weekly
    groups:
      <ecosystem>-minor-patch:
        update-types: [minor, patch]
```

Minor and patch arrive as one pull request per run. **Majors stay ungrouped.**
A major bump is where breakage lives, so it gets its own review and its own
revert. **Security updates stay ungrouped too**, because `applies-to` defaults
to `version-updates`, so a fix still lands alone and immediately. Weekly is the
standard cadence. This repository is the exception at `daily`, because the
catalog's own pins are every consumer's pins and a bump here propagates to every
consumer.

**Dependabot can only bump a reference that carries a comparable version**.
`node:26-alpine` it can advance. `debian:bookworm-slim` is a codename with
nothing to compare, and a bare `busybox` has no tag at all. Version-pin before
adding the watcher, or the entry is a watcher that finds nothing.

**The two container ecosystems read different files and neither one watches what
you build.** `docker` reads `FROM` in Dockerfiles; `docker-compose` reads
`image:` in compose files. Your own published image is CI's output and is not
Dependabot's business. A repository whose base images are pinned in a Dockerfile
and whose service images are pinned in compose needs **both** entries. One does
not reach the other's file.

**A PlatformIO repository watches nothing beyond actions.** Dependabot has no
`platformio` ecosystem, so those pins stay manual.

## Shared infrastructure — aurum-alpha/workflows

Reusable workflows live at `.github/workflows/job-*.yml`, because GitHub
allows no subdirectories there. Composite actions live in subdirectories:
`setup/node-pnpm` and `.github/actions/ci-ok`. Callers reference both at
`@main` (rule PIN).

## Standard repository layout

The catalog is opinionated about where code lives, and **it does not enforce
it**. Those are two different things.

The layout below is the standard answer, and a repo that differs is a repo to
fix. What the shared jobs enforce is narrower: the toolchain. One pnpm, one
TypeScript, one set of steps in one order. That is the *runner*, not the tree.

**Three directory names, and they mean the same thing everywhere:**

| dir | holds | present when |
|---|---|---|
| `client/` | the React app. `vite.config.ts` sets `root: client`, `outDir: ../dist/public` | the repo ships a browser UI |
| `server/` | the backend. Entry is always `server/index.ts` (or the language's equivalent) | the repo ships a service |
| `shared/` | code both sides import | **only when both sides are the same language** |

`shared/` is not a junk drawer and not automatic. A React + Go repo has no
`shared/`. The two halves cannot import each other's source, so a directory
claiming they can is a lie. Where a repo builds two servers in the *same*
language, `shared/` is exactly right, and the rule is unchanged: shared source
requires a shared toolchain.

Build outputs are equally fixed: `dist/public` for the client bundle,
`dist/index.js` for the server bundle. The image copies those two paths and
knows nothing else about the repo.

**A repo that differs is a repo to fix.** `web/` is not an alias for `client/`;
it names a medium rather than a deployable unit.

`workdir` remains:

| shape | package.json | `client/` is |
|---|---|---|
| JS repo | at the root | a source directory |
| JS inside another tree | at `client/` | its own pnpm project |

A Go repo with a React UI has a second `package.json`, a second lockfile and a
second `.node-version` under `client/`, and no rename changes that. `workdir`
distinguishes the two shapes and is legitimate.

`workdir` defaults to `.`; `client` is the second documented shape; any other
relative path holding a `package.json` is accepted. The job validates that the
path is relative, stays inside the repository, and holds a `package.json`. It
fails by name after checkout rather than six steps later inside pnpm.
`tools/check-ci-conformance` (rule WD) makes the same checks against the
caller's stub. Standardising the path would buy uniformity in the one
dimension where variance is free, at the cost of adoption where it is
expensive.

The layout table is enforced by review, not by a job refusing to run.

### The shape of a TS client+server repo

A repo holding a React client *and* an Express server under one `package.json`
converges on the shape below. The shared jobs then need no per-repo inputs
beyond which unit they are pointed at.

| | standard |
|---|---|
| unit source | `client/`, `server/` |
| test files | `*.test.ts(x)` colocated under the unit dir |
| vitest `include` | **absent**: the job passes `--dir client\|server` |
| client bundle | `dist/public` (vite default target) |
| server bundle | `dist/index.js`, esm, `--packages=external` |
| `start` | `node dist/index.js` |
| build scripts | **none** |

The vitest `include` line matters most: while it pins every test to
`client/`, pointing a job at `server/` finds nothing however the DAG is drawn.
A hand-curated `script/build.ts` with an external-package allowlist rots the
same way. So the shared job owns
`esbuild --platform=node --bundle --packages=external --format=esm`, and repos
keep `server/index.ts` as the entry point and no build script.

**A unit with no tests warns, it does not block**. The job runs with
`--passWithNoTests` and a step that counts test files and emits a warning
annotation when the count is zero. **A real test failure still fails the
job**. Blanket `continue-on-error` would suppress genuine breakage too.

### Dev mode: the server never imports vite

Vite is a dev server and a frontend build tool. Nothing in `server/` is
permitted to reference it: not behind `NODE_ENV`, not behind a dynamic import,
not at all.

The standard is **`vite dev` on its own port, proxying `/api` to the backend**;
one `dev` script starts both, under `concurrently -k` so Ctrl-C stops the pair.

**Ports are not decided here.**
[`016-local-development.md`](016-local-development.md) governs what a container
binds, what a host publishes, and where the numbers come from. The proxy target
is read from `PORT`. So the two processes agree without either one naming a
number.

The middleware-mode arrangement, Express hosting vite in-process behind
`NODE_ENV`, is retired. The bundler follows the import, and `vite` is absent
from the runtime image, so the image cannot start. Guarding the import is the
same defect with a condition on it. Removing the reference is the fix, and it
makes `client/` a genuinely independent unit.

### The artifact must start, and CI must say so

An unconditional import of the dev server in `server/index.ts` reaches the
bundle:

```ts
import { setupVite, serveStatic, log } from "./vite";   // -> imports "vite"
```

`vite` is a devDependency. The runtime image runs `pnpm install --prod`. So the
bundle top-level-imports a package the image does not contain.
`node dist/index.js` dies at module resolution with `ERR_MODULE_NOT_FOUND`
before a line of application code runs.

Three rules follow:

1. `job-build-js-esbuild` passes
   `--define:process.env.NODE_ENV='"production"'`. A production bundle built
   without a production NODE_ENV is a contradiction, and it fixes the guarded
   case.
2. The same job then **asserts the property instead of trusting the flag**:
   every bare specifier the bundle imports must appear in `dependencies`. No
   flag can fix a static import, so the check does not depend on one.
3. Production-safe helpers (`serveStatic`, `log`) live in a module that does not
   import vite; only `setupVite` stays behind the dynamic import.

### Module format: `.cjs` by extension is not a module system

The catalog emits `--format=esm` to `dist/index.js`, which under
`"type": "module"` is ESM. A bespoke build emitting `format: "cjs"` to
`dist/index.cjs` works by extension alone. `__dirname` exists in such a repo
only as a side effect of that CJS bundle:

```ts
const distPath = path.resolve(__dirname, "public");   // undefined under ESM
```

The server throws on startup the moment the format changes, invisible to every
gate that never starts the container. Moving onto the standard format
therefore carries three things. `import.meta.dirname` (or
`fileURLToPath(import.meta.url)`) replaces `__dirname`, the `start` script
becomes `node dist/index.js`, and a local boot of the built artifact precedes
the pull request.

## Standard job catalog

Every repo adopts the standard DAG with these canonical job ids, each job's
YAML is byte-identical across repos, and literal duplicates live in
`aurum-alpha/workflows`. **Nothing is extracted before it is identical in
more than one repo**: a shared job codifies an agreement that already exists.
Where a repo lacks a job the catalog defines, it adopts the shared job; it
never writes a bespoke one.

Typed inputs (`workdir`, `dir`) carry repo-specific paths as data, so a job
stays identical across repos.

**Deleting a catalog job breaks its callers immediately, and that is the
mechanism**. Every reference is `@main`, so a caller pointing at a deleted
file cannot load its workflow. The repository then converges on the job that
owns the capability. No deprecation window is offered: it would only let the
old answer survive long enough for someone to write a third.

### Canonical script names (ALL stacks)

Same names everywhere; the runner differs per stack (`pnpm run` /
`composer run` / make targets). Specific names, not generic ones: the *type*
of check is in the name.

| Script | TS | Go (tools/checks or make) | PHP (composer) |
|---|---|---|---|
| `build` | `vite build` | one `go build` per binary per arch → `bin/` | asset/app build |
| `lint` | `oxlint <dir> --type-aware --deny-warnings` | golangci-lint / vet wrapper | phpcs/pint (when adopted) |
| `format` | `prettier --check <dir>` | `gofmt -l .` | phpcbf (when adopted) |
| `typecheck` | `tsc -b --noEmit` | `go vet ./...` | `phpstan analyse` |
| `test:unit` | `vitest run [--dir <unit>] --passWithNoTests --coverage` | `go test ./... -cover` | phpunit unit suite |
| `test:integration` / `test:e2e` | where they exist | `-tags=integration` | phpunit integration / playwright |

Tooling convergence: oxlint + vitest are the TS standard. The full set, the
shape rules that decide which repo carries which, and the reasoning are
[`015-commands.md`](015-commands.md); this table is the summary. The Go and
PHP columns describe real wrappers, because those ecosystems have no
equivalent of `pnpm exec`.

### TS job catalog

Every job: checkout → setup-node (`node-version-file`) → pnpm setup → frozen
install (store-cached) → its one tool. All SHA-pinned, least-privilege. The

- `job-build-js-esbuild`: the server bundle to `dist/index.js`, asserting every

- `job-fmt-js-prettier`: `prettier --check <dir>`.
- `job-typecheck-ts-tsc`: `tsc -b --noEmit`.
- `job-test-unit-js-vitest`: `vitest run --coverage`, publishes `coverage-*`
  and `testresults-*` artifacts (1-day).
- `job-depcheck-js-knip`: `knip --dependencies`, unused packages per unit.

### Go job catalog

- `job-go-mod`: `go mod download && go mod verify`, saves the module cache.
- `job-go-build`: one `go build` per binary per arch, uploads binaries

- `job-go-fmt`: `gofmt -l`.
- `job-go-vet`: `go vet`.

### Run-level job catalog

These read a Dockerfile, a lockfile, a `ci.yml` or an artifact another job

### The Go baseline: every Go codebase runs the same seven

The seven are `mod`, `build`, `fmt`, `vet`, `test-unit`, `lint` and
`govulncheck`. A shared job with zero adopters is not a standard, it is a
file: either every Go repo lints or the job must not exist.

`test-integration` is the honest exception. It belongs wherever integration
tests exist, and a repo with none has none. Absence there is a fact about the
repo, not a missing job.

**Anything beyond those seven is repo-specific and needs a reason**.
A forbidden-import check, a conformance suite, a telemetry canary, an
expand-only migration check, a header check: those are policy about *that*
codebase. That is the legitimate case under Principle 19: a debt with a name.

### Lockfile scanning is not a Go job, and the job is not ours

Every repo scans its dependency lockfiles for known vulnerabilities: **every
one**, not only the Go ones. The scanner reads lockfiles per ecosystem, so its
scope is every repo that has one.

**It does not duplicate `job-go-govulncheck`, and neither replaces the other**.
`govulncheck` is Go-only and call-graph aware, so it reports an advisory only
when the code reaches the vulnerable symbol. `osv-scanner` is lockfile-based
and cross-ecosystem, with no reachability filter. Drop one and either the "is it
reachable" answer goes or every pnpm lockfile is unscanned.

#### The catalog wraps it, and only because the event decides the workflow

Upstream ships **two** reusable workflows, and which one is right depends on
the event:

| workflow | event | reports |
|---|---|---|
| `osv-scanner-reusable-pr.yml` | `pull_request`, `merge_group` | only what the change **introduces** |
| `osv-scanner-reusable.yml` | `push`, `schedule` | **everything** in the tree |

Calling the second one on both events judges a pull request against the whole
backlog. The only lever that stops that blocking unrelated work is
`fail-on-vuln: false`. That also stops the scan blocking a vulnerability the
pull request just added. One flag, two questions, and the answer to the more
important one is lost silently.

`job-osv-scan.yml` selects by event and gives them separate answers:

```yaml
  osv-scanner:
    uses: aurum-alpha/workflows/.github/workflows/job-osv-scan.yml@main
    permissions:
      actions: read
      contents: read
      security-events: write
    with:
      scan-args: |-
        --lockfile=./pnpm-lock.yaml
```

`fail_on_new` defaults **true**: a pull request is blocked by what it
introduces, from day one, in a repo with a backlog. `fail_on_existing`
defaults **false**. That is the Principle 3 stabilization window, held per repo
until its count reaches zero, then flipped. The window is applied to the half
that deserves it rather than to both because they shared a flag.

**Every line of `job-osv-scan.yml` forwards; nothing in it scans**. The test
that keeps a wrapper honest is whether it would still be needed if the
capability had one upstream entry point. This one is only needed *because*
there are two.

**What it buys.** The alternative to wrapping is two jobs per caller with
opposing `if:` conditions, two permissions blocks and the lockfile list
written twice. Wrapping also puts `upload_sarif` in one place, so flipping its
default is one edit here rather than one per call site.

**`upload_sarif` defaults true**, because findings belong in the Security
tab (triaged, dated, assignable) rather than in a job log nobody opens. Two
things keep that honest. A license is org-wide but **enablement is per
repository**, so acceptance is not guaranteed by billing alone. And an upload
that is refused fails the step and takes the scan's verdict with it. So a wrong
assumption here turns every caller's osv job red at once. The caller-side
lever is `upload_sarif: false` with the reason at the call site.

Direct calls to third-party reusable workflows are allow-listed in the checker
(`EXTERNAL_JOBS`, `EXTERNAL_PERMISSIONS`), and the list is empty. A caller
grants permissions once for the whole `uses:` and must hold the union of what
any job in the file requests; `check-caller-permissions` holds that.

#### Wiring

* **Named, never discovered.** `scan-args` lists each lockfile explicitly with
  `--lockfile=`. The action's default is `-r ./`, and recursive discovery is
  the one behaviour we do not take. A scan that finds its own inputs silently
  stops covering a file the day it moves, and reports the same clean result
  either way. A named lockfile that is missing exits 127 and writes no report,
  which fails the job.
* **`upload_sarif` stays at its default of true.** A private repository
  without code scanning enabled sets it false, with the reason at the call
  site. `security-events: write` is granted regardless, because the upstream
  job requests it whether or not the upload runs.
* **No `secrets:`.** `secrets: inherit` into the catalog is right and required.
  Into a third party it is a standing grant of every token the repo holds, for
  a job that needs none. `check-ci-conformance` refuses it.
* **DAG position: a standard gate**. It takes the same `needs:` on the repo's
  build jobs as the rest of that tier and is named in `ci-ok`. The edge buys
  ordering, not data.
* **`runs-on`** is passed from the caller as
  `${{ vars.RUNNER || 'ubuntu-26.04' }}`; the job is a Docker container
  action, so a self-hosted runner label must have Docker available.
* **A PlatformIO repo has nothing for this gate to scan.** PlatformIO resolves
  `lib_deps` from `platformio.ini` at build time and writes no lockfile
  osv-scanner reads. The exclusion is written down so nobody reads the absence
  as an oversight, and it ends the day the repo commits a lockfile.

### PHP job catalog

`builder-image` (tier 2, reusable) → `client-ts-react-build` → `build` →
`test-unit` / `static-analysis` in parallel → `test-integration` (service
containers) → `test-e2e` (compose) → `image` → `ci-ok`. It stays repo-local
until a second PHP caller exists, because the catalog holds capabilities more
than one repository shares.

**One build, one artifact**. `build` runs the repo's Makefile and emits the
complete deployable tree: PHP, vendor, React bundles, CSS, images, scripts.
The vendor tree ships (Principle 21), but it ships *inside* that artifact;
publishing it on its own would be handing an intermediate between jobs. There
is no dev-dependency job either: the dev tree does not ship, so it is a cache,
and `test-unit`, `static-analysis` and `test-integration` install it
themselves.

**The React compile stays its own job**, because it is a compile and the three
React gates hang off it. `build` consumes its artifact.

**The gates hang off `build`, across both stacks**. They read source, so the
edge is ordering rather than data. It couples the stacks on purpose. The two
artifacts ship in one run at one version (Principle 15), so a failed React
compile means nothing ships.

### When Make is the right tool

Make is a fileset transformer: it maps patterns of input files onto output
files and rebuilds only the outputs whose inputs are stale. That is the only
reason to adopt it. The test before adding a Makefile is two questions, both
of which must answer yes. **Is there a real file-to-file transform here, and
does no toolchain already own it?**

A PHP monolith assembling a deploy tree passes. Pattern rules map hundreds of
files from a source layout into the deployable tree, which is not a compile,
so composer cannot do it. A Go service fails on its own evidence. Every one of
its targets is `.PHONY`, so make can never skip anything, and `go build` does
its own staleness checking. That is a task runner wearing a build system's
syntax, and task running is what shell is for.

Everything else fails the second question. `go build` keys a content hash of
sources *and flags*, vite walks a module graph, `tsc` keeps `.tsbuildinfo`,
PlatformIO owns `.c → .o → .elf`. Make compares mtimes and cannot see flags,
so layered over any of them it cannot be more correct, only less.

So Make is not a tier-1 runner-image dependency. A repo entitled to it runs
its Makefile inside its own tier-2 container, and a GitHub-hosted runner has
make already. Go repositories do not convert to it: they have no transform of
their own to describe.

| Job id | needs | Does |
|---|---|---|
| `build` | — | `pio run` env matrix → firmware artifacts (BUILD-ONCE) |
| `test-unit` | build | `pio test` native suite (`job-test-unit-cpp-pio`) |

Toolchain pins: platform versions in `platformio.ini`; Python via setup-python

### An image job does one thing, three times

A single image job that placed artifacts, built, started and pushed reported
one check for four claims. It also took the union of their permissions:
`packages: write` on every pull request in every caller.

Split along the claims:

| job | claims | permission | runs |
|---|---|---|---|
| `job-image-build` | the Dockerfile assembles from artifacts this run already built | `packages: write` | every run |
| `job-image-starts` | the image boots | `packages: read` | every run |
| `job-image-publish` | these tags now point at that image | `packages: write` | tags on main only |
| `job-image-prune` | old staged manifests are gone | `packages: write` | after `ci-ok`, main only |

**The handoff is a digest, not a tag.** `job-image-build` pushes with
`push-by-digest=true` and no tag at all. The manifest is addressable and
unlisted: `starts` pulls it, `publish` promotes it, and nothing appears in the
package's tag list until main. The alternative, a `ci-<sha>` staging tag,
leaves one dead tag per commit per image forever, since GHCR has no TTL.
Addressing by digest also means the split starts the exact manifest publish
promotes, rather than a copy `--load`ed into the runner's daemon. So the thing
tested and the thing shipped are the same bytes.

**`latest` is main's tag, and only main's**. A pull request that could claim it
would silently redirect every deployment pulling by that tag to unreviewed
code. The tag itself carries no evidence of where it came from.

Three things hold the line. The default rule emits `latest` only under
`enable={{is_default_branch}}`, and the promotion step runs only on a push to
`main`. `extra_tags` is rejected if it produces `latest`, and the computed tag
list is checked again afterwards in case some other spelling gets there.

**`imagetools create` moves no layers.** Publish is a registry-side manifest
operation. There is no second build that could differ from the gated one, which
is Principle 17 stated in bytes instead of intent.

**A label is decided at build, so the version label is `job-image-build`'s**.
Labels live in the image config and are fixed when the image is built.
`imagetools create` writes a manifest pointing at bytes that already exist and
changes nothing inside them. That is why the version reaches `job-image-build`
as an input (`stamp`, see **One versioning implementation**, above).

**The Dockerfile in the repo, run as-is.** Every deployable copies artifacts
earlier jobs already built. So `job-image-build` decides nothing beyond which
file, which stage, and where the artifacts go. That last one is the
`artifacts:` input, `client-dist=dist/public`, the same `name=value` idiom as
`start_services`. An image job that rebuilds its own inputs is testing a build
that never ships (Principle 7, BUILD ONCE).

**The prune keys on three things, and the middle one is the trap**: untagged,
*unreferenced*, and older than the threshold. After every publish the staged
manifest `:latest` resolves to is itself untagged. So the job sweeps only
digests outside every tag's reference set, and deletes nothing if it cannot
inspect a tag.

**The prune is the one job outside `ci-ok`.** It runs downstream of the
rollup, main only. Housekeeping that fails says nothing about the commit. A
merge blocked on a registry API hiccup is a worse outcome than a week of extra
blobs. Rule D6 exempts it by name rather than by inference, and requires it to
need `ci-ok` so it cannot run ahead of the gates.

### The rollup is shared; the `needs:` list is not

`ci-ok` is the one job every repo has, and per-repo copies of its fifteen
lines drift into different answers to what a red rollup means.

Split it where the seam actually is. The **`needs:` list is the repo's own
DAG** and cannot be shared; that is the whole content of the job. The
**verdict logic** is the same everywhere and had no business differing.

So the body lives in `aurum-alpha/workflows/.github/actions/ci-ok`, and the
caller keeps what is genuinely its own:

```yaml
  ci-ok:
    needs: [server-go-build, server-go-vet, client-ts-react-build, image]
    if: always()
    runs-on: ${{ vars.RUNNER || 'ubuntu-26.04' }}
    permissions: {}
    steps:
      - uses: aurum-alpha/workflows/.github/actions/ci-ok@main
        with:
          needs_json: ${{ toJSON(needs) }}
```

**No checkout, and no permissions**. The action reads the needs object passed
to it and no repository file, and the runner fetches an `owner/repo/path@ref`
action by itself. `permissions: {}` leaves none, so a checkout would fail
outright against a private repository. The rollup is the one job in a repo
that can honestly declare an empty grant, so it declares one.

The exception is the catalog repo itself, which uses the local path form
`./.github/actions/ci-ok`. That way a change to the action is gated by the run
that ships it. A local action must be in the workspace, so that form does need
its checkout. Rule RU carves it out by name rather than by a looser match.

**A composite action, not a reusable workflow, and the reason is the check
name**. A called workflow reports as `<caller job> / <callee job>`, so `ci-ok`
as a called workflow becomes `ci-ok / ok`. The required status check in every
repo's branch protection then stops reporting at once. A composite action
runs inside the caller's job, so the check keeps its name and only the body is
shared. Where a rename is free, prefer the reusable workflow; where the name
is load-bearing outside the repo, it is not free.

**Pass `toJSON(needs)`, never `toJSON(needs.*.result)`**. The flattened form is
a bare list of verdicts, `["success","failure","success"]`, so a red rollup
can say that something failed and never which thing. The full object is keyed
by job id, which is the only information a reader of a red `ci-ok` is there
for.

**`cancelled` is reported separately from `failure`**, because they mean
opposite things. A failure is a verdict about the code. A cancellation is
almost always the concurrency group superseding an older run, or a runner
going away, and nothing was learned about the commit.

Rule **RU** enforces all four. They are the shared action, the unflattened
context, no local copy of the body, and no checkout in a caller using the
remote form.

### The prelude a bespoke job may not rewrite

A repo's pipeline is shared jobs plus, where Principle 19 applies, a handful of
local job bodies: a repo's own golden-corpus or contract gates. Those bodies
are legitimately local. **Their Node setup is not**. Reaching a working `pnpm`
is the same steps in every repo. A bespoke job that spells them out again is a
second answer to a question the catalog already answers.

`setup/node-pnpm` is that answer for a steps-level consumer. It is a composite
action, because a bespoke job needs a *prelude*, not a whole job body, and a
reusable workflow cannot supply one. Callers reference it at `@main` like
every other first-party surface.

**Every composite gets its own Dependabot `directories:` entry the day it is
added**. `directory: /` reaches `.github/workflows` and a root `action.yml`
and nothing else. actionlint lints workflows, not action manifests. A
composite outside `.github/` therefore has exactly one instrument watching its
pins, and it has to be named.

### Job ids name the deployable unit

Rule **ID** holds the grammar, read against the `capability=` of the catalog
workflow the job calls:

```
(?:[a-z0-9]+-)*<capability>(?:-[a-z0-9]+)?
```

It is loose in front and strict at the end. **Everything before the
capability is optional and unordered**: purpose, language, framework, product,
in whatever combination a repository finds clear, or nothing at all. A bare
`osv-scan` is legal, because a repository with one caller has nothing to
disambiguate. **One optional segment after it is the tool slot**, which is
what lets `server-go-lint-errcheck` and `server-go-lint-staticcheck` differ
while both plainly calling lint.

**A second clause covers the case the first cannot see**. When one repository
calls the same catalog workflow twice, no caller is permitted to hold the bare
capability. Whichever kept it would read as *the* one and its peer as a
variant, when they are peers. A repo calling `job-image-cached` twice, for the
builder image and the production base, names them `build-image-cached` and
`base-image-cached`.

The rule does not compare the id's language segment to the declaration's
`language=`. The segments in front are unordered and unlabelled, so no field
can be pointed at and called the language. Guessing by position fails the
first legal id that puts product before language.

The rule resolves a job through an `aurum-alpha/workflows/...@main` reference.
This repository's own `ci.yml` calls its jobs by local path, so review holds
it to the rule. The local path lets a catalog pull request run the rules *as
the pull request changes them*, not the rules already on `main`.

The convention below is the recommended shape of the prefix:

```
client-ts-react-build          server-go-build            ← no framework slot
server-ts-express-lint         server-php-ci4-test-unit
firmware-cpp-arduino-build     billing-py-django-test-unit
```

**purpose** is what the unit *is*, and the first thing a reader wants. Use the
role when there is one of a kind (`client`, `server`, `service`, `worker`,
`cli`, `firmware`, `lib`). Use the unit's **name** the moment there are several
(`billing`, `auth`), because with three Django services the language stops
discriminating and only the name does. `lib` is the one purpose that is not
deployable, and earns a place because its tests are otherwise homeless.

**language** comes second where present: `ts`, `go`, `php`, `cpp`, `py`.

**framework** is optional, and *always beneath a language*, never beside it.
There is no CodeIgniter for Go and no Nest for Python. A framework never floats
free of the language it is written in, so it can never occupy the language
slot. `react`/`express`/`nest` are ts; `ci4`/`laravel` are php;
`django`/`fastapi` are py; `arduino` is cpp. Where a unit has no framework (Go
here) the slot is simply absent, and that absence is accurate rather than
missing.

The two middle tokens are not redundant: **they select two different tiers of
tooling**. `client-ts-react` says both the language tier (`tsc`, `oxlint`) and
the framework tier (`vite build`) apply to it. `server-go` says only the
language tier does.

**Name the framework whenever there is one, even when it owns no build tool.**
Naming and the job catalog are independent decisions:

- the framework token is *identity*, present whenever a framework is in use
- a framework-tier *job* exists only where the framework owns a tool

So `server-ts-express-build` names Express and calls a language-tier build job;
Express is a request-routing library and owns no bundler. The name says what
the unit **is**, the job says what **runs** it. Replacing Express with Nest is
a consequential change the id must show. An empty framework slot on
`server-ts` says exactly that: no framework, a custom build.

**A job spanning more than one unit takes no purpose prefix**. Those are
`image`, `package`, `release`, `test-e2e`, `changes`, `ci-ok`, and a repo-wide
`typecheck` where a single `tsconfig.json` genuinely covers every unit. The
absence marks the convergence and rollup jobs.

### Capability names: category first, specialisation second

`test-unit`, `test-integration`, `test-e2e`, not `unit-test`. English says
"unit test". We invert it, for the same reason purpose comes first in a job
id: **the general category leads, so families group.**

```
test-e2e            e2e-test
test-integration    integration-test      ← scattered
test-unit           unit-test
```

Sorted, listed in a checks UI, or grepped, the inverted form keeps every kind
of test together and makes a missing one visible. Any capability with variants
takes the family name first and the variant second; capabilities with no
variants stay single words (`lint`, `build`, `typecheck`, `fmt`, `vet`). And
`lint` is not a member of the test family however much it feels adjacent.

### One linter

`job-lint-js-oxlint` is the JS linter, and there is no second one.
`config/.oxlintrc.json` is byte-identical in every repo, and
`check-lint-configs` fails the build if a repo edits it. Type-aware rules run
through `--type-aware` (oxlint-tsgolint, built on typescript-go); eslint
plugins oxlint has not ported run through its JS plugin bridge.

**oxlint has no dependency on the `typescript` package, and that is what
unblocks TypeScript 7**. TS 7 is the native Go port whose default export is
`version` and `versionMajorMinor` alone: no `createProgram`, no
`TypeChecker`. `oxlint-tsgolint` ships its own typescript-go binary. For the
same reason, do not adopt `ts-node`, `ts-jest`, `typedoc`, `ts-morph` or
`tsup`. Each re-imports that API and would re-pin every consumer to
TypeScript 6.

**`eslint-plugin-react-hooks` and `eslint-plugin-react-refresh` stay**,
consumed by oxlint through its JS plugin bridge; 14 of the 16 react-hooks
rules arrive that way. They peer-depend on eslint, so `eslint` remains in
every lockfile transitively. It is not a direct dependency and is not run
anywhere.

`oxlint` and `oxlint-tsgolint` are asserted in `dependency-versions.json`,
exactly pinned, like every other converged package.

**The gate is open because of debt, not because of the linter**. Every oxlint
caller is `warn_only`, on account of the errors and warnings already in the
tree. That is exactly the stabilization window Principle 3 describes:
findings visible, gate open, flipped when the count comes down. The cost is
that the only JS lint job blocks nothing, so a regression lands silently, and
burning the debt down is what closes it.

### One formatter, and why it does not get a stabilization window

`job-fmt-js-prettier` is the JS/TS formatting gate. The config is `semi: false`
and `singleQuote: true`, chosen to match the hand-written codebases: a
decision someone made outranks a default nobody chose.

`config/.prettierrc.yaml` is byte-identical in every repo, and
`check-lint-configs` holds it there, the same arrangement `.oxlintrc.json`
has. It carries **two keys**. Everything else is prettier's own default, and a
config that restates defaults is a config whose lines nobody can justify at
the next upgrade.

**There is no shared `.prettierignore`**. Prettier 3 defaults `--ignore-path`
to `[.gitignore, .prettierignore]`, so build output, coverage and
`node_modules` are already out of scope with no file at all. What remains is
genuinely local, and Principle 2 places it in the repo as configuration the
tool reads.

**This gate blocks on day one**, and that is where it differs from oxlint.
Lint debt has a gradient: fixing findings in files already being edited moves
the count, so an expiry can be stated. Formatting has none: a file is
prettier-clean or it is not, and the whole debt clears with one
`prettier --write` per tree. So no expiry exists that anyone could write down.
A `warn_only` formatter would be a permanently red check with no mechanism
attached, the thing Principle 3's ticket-and-expiry clause prevents.

The `warn_only` input exists on the job for contract symmetry. The window it
buys is one pull request wide: reformat in a pull request that changes nothing
else, then turn the gate on.

Prettier is an ordinary devDependency, exactly pinned per repository like
oxlint and tsc. The job runs `pnpm exec prettier --check` with the same
prelude as every other JS job. A `pnpm dlx` gate has no script that can mirror
it, which [`015-commands.md`](015-commands.md) DC2 and DC5 forbid.

`dependency-versions.json` asserts prettier's version; a repository that has
not adopted is skipped and held to it the moment it adopts.

**It is named for the tool, because the tool is likely to change**. `oxfmt` is
prettier-compatible by design and pre-1.0, and a formatter rewrites every file
it touches. So `job-fmt-js-prettier` makes the eventual `job-fmt-js-oxfmt` a
visible rename rather than a silent change of behaviour.

### Unused dependencies

`job-depcheck-js-knip` reports packages a unit declares and never uses.
Agreement is not evidence of use. A package at one version across every repo
declaring it looks converged and can be dead everywhere, which a version survey
cannot see.

**One lane**. A two-lane design, block on unused `dependencies` and warn on
`devDependencies`, is what `knip --production` expresses. Production mode
misreports: it flags `express` as unused in an express server whose entry
point it does not report as unreachable. `devDependencies` is not one of
knip's issue types either, so `--exclude devDependencies` silently excludes a
type that does not exist. A gate whose findings cannot be trusted is worse
than none, because someone eventually deletes a package it named.

**Two false-positive classes the job handles, and one it cannot.**

- *Binaries the catalog invokes.* `oxlint` and `oxlint-tsgolint` are reported
  unused and are not. The invocation lives in `job-lint-js-oxlint`, outside the
  package, so nothing in the repo tells knip they are used. That is structural
  to the catalog design, so the baseline lives in the job rather than in every
  repo.
- *Plugins that need a live environment.* knip's drizzle plugin loads
  `drizzle.config.ts` and dies without a `DATABASE_URL` no lint-shaped job has.
  It is disabled in the generated config; `drizzle-kit` is still detected
  through the `db:push` script, so nothing is lost.
- *Packages reachable only from dead files.* knip prunes unreachable files
  first, so a package imported solely by a scaffolded-but-unused component reads
  as unused. The finding is true, and clearing it means deleting the dead
  component **and** removing the package.

**The entry patterns are an input, because a hardcoded list produces a wrong
answer with no error**. Files knip cannot reach from an entry point are
pruned. So a default list that misses a multi-page app's entries reports that
app's packages as unused, with the only hint buried in normal output.

So `entry` is a caller input, and it REPLACES the default rather than adding to
it. An entry list describes one tree's shape, and a pattern from a different
shape is noise rather than a harmless extra. An empty value fails the job. A
knip with no entry points prunes everything and reports every dependency
unused. That reads as a catastrophic finding rather than as a broken config,
and under `warn_only` reads as nothing at all.

**Prove a gate on the input that makes it fail, not on the one that makes it
pass.**

**The job fails on a knip error even under `warn_only`, and that is not
belt-and-braces**. The knip exit code tracks findings only: a config it could
not load prints `ERROR` and still exits 0. A job that runs knip and trusts `$?`
therefore reports success having analysed nothing. Principle 3's stabilization
window is a decision to tolerate known debt, never a decision to tolerate a
broken analysis. The two outcomes are separate steps so a red check names
which one happened.

### Shared job names: named for the tool where the tool is likely to change

A caller names the **unit**; a shared job names the **tool it runs**. The
files on disk follow two shapes. Go jobs are `job-go-<function>`, because
`go test`, `go vet` and `gofmt` are Go itself and a tool token would add
nothing. JS jobs are `job-<function>-js-<tool>`, because the tool is the part
likely to change:

```
job-go-build           job-go-fmt             job-go-vet            job-go-lint
job-go-test-unit       job-go-govulncheck     job-go-mod
job-build-js-vite      job-build-js-esbuild   job-lint-js-oxlint    job-fmt-js-prettier
job-typecheck-ts-tsc   job-test-unit-js-vitest                      job-depcheck-js-knip
job-build-cpp-pio      job-test-unit-cpp-pio
```

Swapping vitest for jest is then a visible rename, `job-test-unit-js-jest`,
rather than a silent change of behaviour inside a file whose name never moved.

Language here is the **tool's ecosystem**, not the source's. The vitest runner
is JavaScript and happens to read TypeScript, so it is `js`. By contrast
`typecheck-ts-tsc` is `ts` because `tsc` exists only for TypeScript. A caller
written in TypeScript therefore calls a `js` job, and that is correct: the
caller names its source, the job names its tool.

**Jobs with no language token.** Some shared jobs act on the *run* rather than
on a codebase: `job-image-build`, `job-image-publish`, `job-image-prune`,
`job-osv-scan`, `job-ci-conformance`, `job-coverage-upload`. None of them can
be pointed at a language, because none of them reads source. They read a
Dockerfile, a lockfile, a `ci.yml`, or an artifact another job produced. A
language token would be a lie about what the job examines, so these take
`<function>` alone. The test is the same one the language tier uses in
reverse. If changing the repo's language would not change a single line of the
job, it has no language.

**Framework-tier shared jobs.** A framework earns a shared job only when
it owns a tool: React does (`vite build`), CodeIgniter 4 does (`spark test`),
Arduino does (`pio run`). Express does not. It routes requests and owns no
bundler, so its build is a language-tier job. The test for admitting a new
framework job is "what command would it run?"; if there is no single answer,
there is no job.

**Display names = job ids**: no job-level `name:` overrides anywhere. The
lowercase id is what the YAML, the checks UI, and any required-check string
all show. Human context lives in step names and comments.
