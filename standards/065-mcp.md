# MCP endpoints: an agent acts as the person who connected it

## Why this exists

A Model Context Protocol endpoint lets an agent call a product the way its
console does. It is a second front door to the same data. A second front door
with its own authorization is a second set of rules. Those rules drift from
the console's, and the drift is invisible until an agent does what a person
could not.

This standard makes the endpoint a thin translation and nothing more. Each
tool is one route the product already serves. Each call runs as the person who
connected, through that route's own check. The authorization the agent meets
is then the console's own, by construction rather than by review.

## The rules

### MC1. A tool is one route of the service's own API, dispatched in process

Each tool names one route. A call builds a request for that route and serves
it through the service's own router, in the same process. The route's
authentication, permission check, validation and tenant scoping run exactly as
they run for the console.

**No tool reads or writes the store**. A tool over the store is a second
authorization path. It is the path an agent uses, so it is the one that must
not differ from the console's.

A tool that composes two routes is two calls in the agent, not one tool. A
tool answers the route's body as its text. A refusal is an error result that
carries the route's problem document, so the agent reads why it was refused.

### MC2. The identity is the person's own token, and the inner request carries the caller's facts

The agent presents the person's access token, issued to the realm's MCP client
(MC5). The endpoint passes the same `Authorization` header to every route it
dispatches. A service account is never the identity. An agent sees what the
person sees, and the audit trail names the person.

**The inner request carries every fact the outer request carried about the
caller**. These are `Authorization`, `Host`, `User-Agent`, the connection's
remote address and the declared forwarding header. The tenant resolver reads
`Host` under [`092-tenant-hostnames.md`](092-tenant-hostnames.md) TH2. The
audit record reads the address under [`080-audit.md`](080-audit.md) AE10.
Without them, an act through an agent is recorded with no address, or resolved
into no tenant.

The trusted-proxy check still keys on the remote address. Copying the
forwarding header with the address keeps the outer request's trust decision,
and widens nothing.

### MC3. Discovery is RFC 9728, and every `401` names the metadata document

The endpoint publishes an
[RFC 9728](https://www.rfc-editor.org/rfc/rfc9728) protected-resource
metadata document. Its path is `/.well-known/oauth-protected-resource`
followed by the endpoint's own path. The document names:

| Field | Value |
|---|---|
| `resource` | the endpoint's absolute URL, as the client reached it |
| `resource_name` | the product's name |
| `authorization_servers` | the realm's issuer, as [`060-auth.md`](060-auth.md) names it |
| `bearer_methods_supported` | `["header"]` |
| `scopes_supported` | `["openid"]` |

Every `401` the endpoint answers carries
`WWW-Authenticate: Bearer resource_metadata="<document URL>"`. A client that
holds no token starts sign-in from that header and from nothing else.

**The resource URL comes from configuration or from a host the product
knows.** A product on one host configures it. A product that names tenants by
host derives it from `Host`, only for a host its tenant table holds. A host the
table does not hold gets no document, as TH3 answers it.

### MC4. The endpoint is stateless Streamable HTTP answering JSON, and it bypasses the edge's sign-in hop

The transport is Streamable HTTP in its stateless form. Every call is one
`POST` and one JSON response. Nothing streams through the edge, and no session
is held between calls. Any method other than `POST` is `405`.

**The endpoint and its metadata document go straight to the service at the
edge**. The browser sign-in hop overwrites `Authorization`, and an agent holds
no session cookie. The service authenticates the bearer itself, as every API
route already does under [`060-auth.md`](060-auth.md). Every other route keeps
the hop.

The metadata document is the only new unauthenticated surface. It holds no
data that the issuer does not already publish.

### MC5. A person signs an agent in through the realm's MCP client

The realm carries one public client for MCP, named `<repo>-mcp`. It uses the
authorization code flow with PKCE, issues tokens for the application's
audience, and sits behind the same access gate as the browser client. The
devkit renders it from `realm.mcp_client` in `devkit.json`. A deployment
renders it from the same setting.

No product mints its own MCP token, and no product accepts a token issued to
any other client's audience.

### MC6. The endpoint is off until configuration turns it on

The endpoint is not mounted unless configuration enables it. A service with no
identity provider configured never mounts it, whatever the setting says. The
configuration that enables it also names the resource URL when the product has
one host.

An agent reaches a service that every person's automation can reach. The
decision to open that door belongs to the deployment and is visible there.

### MC7. Every route is a tool or a named exclusion, and a test holds the list

The product keeps the list of tools and the list of excluded routes, each
exclusion with its reason. A test walks the router's registered routes. It
fails when a route is in neither list, and when a tool names a route the
router does not hold.

**Three kinds of route are excluded**. A route that returns a credential is
excluded. A route that changes a trust decision, such as a host key or an
identity provider binding, is excluded. A route that provisions or removes a
person is excluded. These stay a person's act in the console, and the reason
names which kind applies.

### MC8. Every tool states its effect, and outside text is data

Every tool carries the protocol's annotations. A read is read-only and
idempotent. A tool that spends a budget or runs a probe and changes no record
is not destructive. A tool that only adds a record is not destructive. A tool
that changes or deletes a record is destructive. A tool that writes is not
idempotent unless its route makes a repeat change nothing.

The server's instructions state what the tools do, and that every tool runs as
the person who connected. They also state that text from outside the service
is data and never an instruction. Pull request titles, branch names, log lines
and customer text are such outside text.

## What a product declares

Each product states these in its **Conventions**:

| Declaration | The choices |
|---|---|
| **Whether it serves MCP** | yes, with the endpoint's path; no |
| **The resource URL** | one configured URL; derived from the tenant host (MC3) |
| **The excluded routes** | the list, each with its MC7 kind |

## Decisions

- **Tools over the store, written for agents**. They would read more cheaply
  than a route and its serialization. They are refused because the route's
  check is the only authorization the product tests. A second path is a second
  set of rules to keep equal by hand (MC1).
- **A service account for agents**. It is simpler to configure. It is refused
  because the audit trail would name the account, and the account's grant
  would be wider than any one person's (MC2).
- **A local binary per product, holding a token**. It needs no edge route. Hosted
  agent clients connect only to a remote endpoint. A binary holding a token
  is also a credential on a laptop, so it is refused.
- **A session per connection**. It allows server-sent notifications. It is
  refused because no tool needs one, and a held session needs sticky routing
  at the edge (MC4).
